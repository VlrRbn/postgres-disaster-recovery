# v0.8.0 — Controlled Switchover And Rejoin

## Summary

Perform an explicit role change in the local PostgreSQL replication runtime:
fence and stop the original primary, promote its caught-up standby, and rejoin
the original primary as a read-only replica through offline `pg_rewind`.

## Highlights

- Check recovery and replay state before promotion and wait for a captured WAL position.
- Verify the original primary is stopped before requesting standby promotion.
- Preserve startup fencing and transition state in a separate control volume.
- Prepare a physical slot for the returning node and configure its recovery connection.
- Resume the promoted or reversed topology across full container recreation.
- Route the existing SQL commands to the current writable or read-only role.
- Extend the existing replication acceptance scenario with promotion and rejoin checks.

## Validation

Local acceptance rejects premature rejoin and paused-replay promotion, verifies
a new timeline and a writable promoted node, and blocks ordinary startup of the
old primary. Rejoin checks both offline clusters with `pg_rewind`, then verifies
reversed WAL streaming, rejected writes on the old primary, and 24 exact records
after container recreation. The tested controlled transition required no block
rewind; recovery of a genuinely divergent old primary is not established.

Static checks and the existing physical backup, restore, and PITR scenario passed.

## Scope

Application writers must be stopped before promotion. The original primary must
be reachable for this controlled procedure. Rejoin briefly stops the new primary
and modifies the old primary's data to follow it; independent write histories
are not merged. Required WAL and clean shutdown are prerequisites for rewind.

This release provides one planned role reversal on one Docker host. It does not
provide automatic failure detection, forced failover, distributed fencing, traffic
routing, reverse switchover, or automatic reseeding after rewind failure.
