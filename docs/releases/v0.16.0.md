# v0.16.0 — Patroni S3 Backup And Recovery

## Summary

Store Patroni full backups and WAL in an optional S3 repository. Reuse the
existing backup and recovery commands to recover a pre-failover backup onto
the promoted timeline without mounting source PostgreSQL or etcd data.

## Highlights

- Select S3 through one backend setting; retain local storage as the default.
- Separate S3 project names, private configuration, and repository prefixes.
- Reuse profile and EC2 instance authentication with verified HTTPS.
- Add optional prefix-scoped writer/reader roles and instance profiles without widening standalone policies.
- Allow inspection and recovery through a separately configured reader identity.
- Keep restored data separate, disable archiving, and preserve existing target guards.

## Validation

The disposable API scenario extends the existing cross-timeline recovery test.
It creates full backups before and after promotion, removes source database
and DCS volumes, and recovers exact records through a TLS endpoint that rejects
object writes and deletes. Untrusted certificates and unreachable recovery
targets fail. Object versions and delete markers remain unchanged through
recovery and restore-container recreation.

Live AWS validation created full backups on both leader timelines and recovered
the original backup through a separate reader role after source shutdown.
The deleted order returned, the post-failover order remained, and the late order
was excluded. A new restored write survived container recreation.

## Scope

The local API fixture validates integration and recovery behavior. No cloud
resources are created by acceptance. The recovered database is standalone;
etcd rebuild, application cutover, and scheduled Patroni backups are outside
this change. Profile credentials require explicit refresh and container
recreation. Live AWS validation used profile authentication on the existing
Docker host; replacement-host recovery and EC2 instance authentication for this
backend remain unverified.
