# v0.7.0 — Streaming Replication

## Summary

Run a separate PostgreSQL primary and read-only standby with asynchronous
streaming replication, persistent volumes, and operational commands for startup,
SQL access, shutdown, and replication status.

## Highlights

- Seed an empty standby with `pg_basebackup`, then stream WAL from the primary.
- Use a dedicated SCRAM-authenticated replication role and private password files.
- Retain required WAL through a physical slot with `max_slot_wal_keep_size=256MB`.
- Resume existing primary and standby volumes without repeating the base backup.
- Inspect sender, receiver, slot activity, and reported replay lag.
- Refuse a nonempty standby target without its recovery marker.
- Keep replication resources separate from the local backup and AWS S3 runtimes.

## Validation

CI passed for merged main commit `cacfa68a7b4bc1348d8086c10916be6008330886`.
The replication scenario compared all stored fields for 22 orders, rejected
standby writes with SQLSTATE `25006`, verified catch-up after a standby outage,
and confirmed readable recovery mode during a primary outage and reconnection
afterwards. Both containers were recreated on retained volumes and the exact
records remained available. Neither service published a host port.

The same main CI passed static checks, 26 unit test methods, existing physical
restore and PITR scenarios, acknowledged-loss measurement, backup health,
the S3 API fixture, pgAdmin acceptance, and both Terraform validation roots.

## Scope

Replication is asynchronous and both services share one Docker host. This release
does not provide zero-loss failover, TLS transport, automatic promotion, traffic
routing, or automatic reseeding after required WAL is lost. Streaming replicates
unwanted committed changes too; backup and PITR remain necessary for recovery
to an earlier state.
