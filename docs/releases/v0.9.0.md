# v0.9.0 — Scheduled Backups And Health Checks

## Summary

Add optional systemd user services and timers for the existing local full-backup
and backup-health commands, with explicit configuration, serialized execution,
and failure output in the user journal.

## Highlights

- Daily full backup at `02:00 UTC`, with randomized delay, and health checks at
  minutes `15` and `45` of each hour.
- Persistent calendar timers request a catch-up activation after missed runs.
- Installation preserves private operator configuration and leaves timers disabled.
- Shared project lock serializes scheduled backup and health jobs.
- Health jobs use a 26-hour backup-age limit to allow margin around daily backups.
- Lifecycle commands show timer/job state, stop future activations without killing
  active jobs, and remove idle unit files while retaining config and backups.
- `make help` lists commands by purpose; `make stop-all` disables installed
  project timers and stops this checkout's project containers while retaining data.

## Validation

The real systemd parser accepts the four unit definitions and both calendars.
Six installer tests verify private configuration, preservation, safe removal,
special-character checkout paths, and the absence of activation during installation.
Six additional tests use stubbed Docker and systemd commands to check stop-all
selection, busy-job guards, and failure handling without stopping real containers.
Disposable acceptance runs the same scheduled job entrypoints as the units:
a verified backup and healthy JSON succeed; contention and a stopped primary
produce nonzero results. Existing backup-health and physical restore/PITR
regressions pass.

Validation on Ubuntu recorded full backup and health services
through the user manager, a health run with a temporary 30-second timer, journal
output, failure with a stopped primary, and recovery after restart. Normal
calendar firing, logout/reboot behavior, and persistent catch-up remain untested.

## Scope

The configured local primary and Docker must be available. Scheduling does not
start PostgreSQL, install external alerts, or schedule AWS S3 jobs. User-manager
lifetime and host uptime govern execution; lingering is an explicit operator
choice. Calendar intervals and health thresholds are not recovery guarantees.
