# v0.12.0 — Standby Recovery After WAL Loss

## Summary

Recover the current standby after required WAL is removed and its physical
replication slot becomes unusable. Keep the writable primary running while
replacing the selected replica from a fresh, verified base backup.

## Highlights

- Add `RESEED_NODE=... make replication-reseed` to the existing operational script.
- Select the replica from saved topology and require its explicit service name.
- Refuse healthy slots, writable targets, unrelated database identities, and
  incomplete role transitions.
- Copy through `sslmode=verify-full` and run `pg_verifybackup` before replacing
  the stopped replica's data.
- Preserve TLS identities, node fencing, and control state outside copied data.
- Block incomplete startup with a persistent marker and allow explicit retry.
- Support both initial and reversed roles after a completed switchover/rejoin.

## Validation

The disposable replication scenario exceeds the configured WAL-retention limit,
checks a `lost` slot and the failed ordinary restart, then reseeds in both
topologies. It also rejects an untrusted CA during copying, checks that the old
data remains intact, verifies blocked startup, and retries successfully.
Source start times, exact records, new writes, read-only roles, and verified TLS
are checked through recovery and container recreation.

Validation on a separate recovery runtime also confirmed reseeding in both
topologies, unchanged writable-source start time during reseeding, and six
synthetic orders retained after container recreation with a read-only replica.

## Scope

This is an operator-triggered rebuild of an existing replica, not automatic
failover or recovery of an unfinished rejoin. Additional tablespaces are not
supported. Allow space for the old database and a complete staged copy, including
WAL. Interrupted replacement is blocked until retried; no historical copy is
retained after success. Both nodes still share one host and replicate
asynchronously.
