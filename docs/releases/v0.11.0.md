# v0.11.0 — TLS For Streaming Replication

## Summary

Require verified TLS for the existing local streaming replication runtime,
including initial seeding, controlled switchover, and replica rejoin.

## Highlights

- Generate and preserve a private per-runtime CA and separate node identities.
- Keep the CA signing key on the host and mount only each node's own server key.
- Use `sslmode=verify-full` and a trusted root for base backup and WAL streaming.
- Reject plaintext replication through a managed HBA file and require SCRAM over TLS.
- Upgrade existing standby connection settings without reseeding retained data.
- Preserve node identities and verified reverse streaming after offline rejoin.
- Show negotiated TLS protocol and cipher in replication status.

## Validation

Certificate setup tests verify private creation, preservation, invalid/mismatched
material rejection, and cleanup on failed generation. The disposable replication
scenario exercises real PostgreSQL TLS, plaintext and trust/hostname failures,
retained-volume startup, outage recovery, promotion, fencing, offline rewind,
and reversed encrypted streaming with matching data.

Validation on existing database volumes also confirmed TLS 1.3,
plaintext/trust/hostname rejection, a new replicated write, and persistence of
data and reversed roles after container recreation.

## Scope

The CA is local to this single-host runtime. SQL administration continues over local
sockets; application TCP access and client certificate authentication are not introduced.
Certificate replacement requires an operator-managed restart; automatic renewal and
distributed PKI are outside this change. Asynchronous replication and the existing
local fencing retain their documented limits.
