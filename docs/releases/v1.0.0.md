# v1.0.0 — PostgreSQL Disaster Recovery

## Summary

The first stable project baseline brings together PostgreSQL backup, recovery,
replication, and failover workflows with reproducible local environments and
verified AWS recovery. It defines the documented operational interface for
future releases and includes the architecture overview and local demo.

This release consolidates the existing runtime. It adds no database behavior
or infrastructure resources beyond the previously delivered capabilities.

## Highlights

- Full pgBackRest backups, continuous WAL archiving, retention, integrity checks, and recovery into a separate data volume.
- Point-in-time recovery with explicit backup labels, UTC targets, and destination timelines, including recovery across Patroni failover.
- Recovery timing and acknowledged-write loss reports with explicit measurement boundaries.
- TLS-protected streaming replication, controlled switchover, former-primary rejoin, and standby recovery after WAL loss.
- A two-node Patroni runtime with a three-member etcd quorum and HAProxy primary endpoint.
- Optional S3 repositories with prefix-scoped writer/reader identities and profile or instance-role authentication.
- Recovery on a clean EC2 host through a reader instance profile, with exact data comparison and temporary-infrastructure cleanup.
- Optional local systemd backup/health jobs and Telegram/SMTP failure and recovery notifications.

## Compatibility

The documented operational commands and required configuration names form the
public interface. Compatible additions use minor versions, compatible fixes use
patch versions, and incompatible interface changes require a major version.
See the [version policy](https://github.com/VlrRbn/postgres-disaster-recovery/blob/v1.0.0/docs/releasing.md#version-policy).

## Scope

The replication and Patroni runtimes share one source Docker host. Replication
is asynchronous, and acknowledged writes can be lost during failover. One
HAProxy instance remains a shared failure point; clients must reconnect and
handle uncertain commit outcomes. Watchdog and external host fencing are not
configured.

PITR produces a separate PostgreSQL instance. Restoring etcd, rebuilding the
Patroni cluster from that result, and application cutover require additional
procedures. Recovery observations are specific to their recorded test conditions
and do not establish an availability or recovery-time guarantee.

Scheduling and notifications cover the standalone local runtime. Host uptime
and user-manager lifetime govern execution; independent monitoring of a powered-off
host and scheduled Patroni backups are outside this baseline. Certificate renewal
is manual. EC2 reader recovery was verified; EC2 writer operation remains untested.
Image rebuilds still resolve transitive dependencies from live repositories.
