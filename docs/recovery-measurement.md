# Recovery Measurement

The first measurement step records one verified PITR attempt and compares its
recovered dataset with the wanted state. Reports are generated by the existing
disposable acceptance scenario; interactive restore commands retain their behavior.

## Run And Read The Report

From the repository root:

```bash
make check
make acceptance
```

After all recovery checks pass, the command prints a report path and a short
summary. Each run creates a separate JSON file under the Git-ignored directory
`.local/reports/`. Use the exact path printed by your run:

```bash
python3 -m json.tool .local/reports/postgres-dr-test-TIMESTAMP-PID.json
```

The report remains after disposable containers, volumes, and temporary secrets
are removed. It contains synthetic row counts, timestamps, a backup label, and
source information. It contains no credentials or row contents. CI prints the
same report in the **Show recovery measurement** step.

## Duration Boundary

| Boundary | Definition |
| --- | --- |
| Start | Immediately before calling the successful time-target restore, after preparing an empty target |
| End | Recovery has ended, exact CSV comparison and exclusion checks passed, and a new restored-side write was read back |
| Clock | The same Docker host's monotonic clock, measured in nanoseconds |
| Included | Wrapper execution, image build/cache check, file restore, WAL replay, readiness wait, and data/write validation |
| Outside the interval | Detection, selecting the target, backup creation, archiving, fault-injection attempts, target preparation, restart checks, and application cutover |

`recovery_duration_seconds` is the observed interval for this one restore. UTC
timestamps show when the boundaries occurred; duration uses monotonic time so
host wall-clock adjustments do not change its value. Both stamps must originate
on the same host in the same run.

The restore image is already present and cached in this acceptance sequence.
The workload contains 22 wanted rows on one Docker host. Treat the value as
evidence for the stated conditions when discussing RTO. It does not establish a
production recovery objective or incident-to-application downtime.

## Data Completeness And RPO

The report compares every stored field in the ordered expected and recovered
CSV snapshots. A mismatch, an empty expected dataset, or inclusion of a known
post-target row prevents a successful report.

- `expected_rows` and `recovered_rows`: rows wanted at the selected recovery point.
- `missing_expected_rows`: zero only after exact comparison succeeds.
- `excluded_post_target_rows`: rows deliberately excluded by the selected target.
- `rollback_window_seconds`: interval from the selected UTC target to the first
  database timestamp observed after the destructive DELETE returned successfully.
- `rpo_seconds`: `null`; this controlled rollback does not measure loss of
  acknowledged workload at an unexpected crash.

The incident observation occurs after DELETE's commit acknowledgment; it is not
an exact PostgreSQL commit timestamp. Row `created_at` values likewise do not
establish transaction commit times. Deliberate rollback and zero missing wanted
rows must not be presented as proof of a universal zero RPO.

The [acknowledged-workload scenario](acknowledged-workload-rpo.md) separately
journals successful commits, causes an archive outage and primary crash, and
measures loss when recovering the last available archived WAL. Its report uses
`observed_rpo_seconds`; the intentional-rollback report retains `rpo_seconds: null`.

## Acceptance And Provenance

`make check` includes report tests: wall-clock reversal with positive monotonic
duration, corrupt or missing rows, included post-target rows, and invalid time
boundaries. `make acceptance` requires the real PostgreSQL PITR scenario,
recovered-side writes, restart persistence, and repository/source isolation to
pass before writing a report. A prior successful run has its own file and cannot
be mistaken for an overwritten result of a failed run.

`source_commit` records HEAD. `worktree_dirty` identifies local runs containing
uncommitted changes; a commit alone is not sufficient provenance for such a run.
The report's `verified` status covers data and recovery checks. Cleanup runs
after report creation; its failure makes the overall command fail even if that
verified report exists. Check the command's final exit status as well.
